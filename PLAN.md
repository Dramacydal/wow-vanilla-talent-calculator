# Standalone (GitHub Pages) версия WoW Vanilla Talents Viewer

Статический вариант сайта без PHP/MySQL на проде. Исходный проект с экстрактором, БД и
Symfony-версией остаётся в `../wow-talents-viewer` и служит только как источник данных
(офлайн-пайплайн: клиент -> MPQ/DBC -> MySQL -> экспорт).

## Решения

- **Роутинг: реальные файлы-заглушки** (по одному `index.html` на маршрут), без
  hash-роутинга и без `404.html`-трюка. Реальные URL, статус 200, свой `<title>` на
  страницу, без редиректов.
- **Иконки, фоны и JSON не коммитим в репозиторий** (контент Blizzard) — всё это живёт на
  **Cloudflare Pages** (отдельный проект «assets+data», заливка через `wrangler`, без git).
  В репозитории GitHub Pages остаются только код и HTML-заглушки.
- Базовый URL CDN — одна конфиг-константа в клиенте, **не** зашитая в данные: JSON хранит
  только хеш иконки (`iconPath`), URL клиент собирает сам. Смена CDN = правка константы и
  перезаливка файлов, ре-экспорт данных не нужен.
- JSON — **подготовленные** файлы, а не дампы таблиц (см. «Формат данных»).
- **Дедупликация билдов (вариант Б).** Подряд идущие билды (порядок по `build_number`),
  у которых данные идентичны **у всех классов**, схлопываются в одну запись. По замеру на
  БД: 22 из 44 билдов идентичны предыдущему, остаётся 22 группы. Группы определяет
  экспортёр автоматически по хешу канонического содержимого (вкладки, иконки, позиции,
  ранги, тексты, стойки, пререквизиты), а не вручную, и пересчитывает их при каждом
  экспорте (данные в БД ещё будут переэкстрактиться).
  - **Представитель группы** по умолчанию первый по `build_number`, но с ручным
    переопределением. Первое переопределение: группа `1.0.0.3980 / 0.12.0.3988 /
    1.0.1.3989` представляется `0.12.0.3988` (остальные два — публичная бета).
  - В интерфейсе в списке билдов остаются только представители, остальные члены группы
    показываются как справка («также: …»), отдельно выбрать их нельзя.
  - По умолчанию: для билдов-членов группы делаем крошечные редирект-заглушки
    (`tree/<член>/<класс>/` -> представитель), чтобы старые ссылки не умерли.
  - Хранение данных по хешу содержимого (`data/trees/<hash>.json`, `data/index.json`
    сопоставляет «представитель × класс» с файлом): класс, который не менялся между
    соседними представителями, хранится один раз (108 уникальных деревьев вместо
    344 пар по замеру). Бесплатно поверх Б; файлы кэшируются бессрочно.
- **CDN уже развёрнут** как Workers static assets (не классический Pages):
  `https://lucky-mud-f0cd.elsoldollo.workers.dev`. Залиты `icons/`, `backgrounds/`,
  `class-icons/` и `_headers`; проверено — 200, `cache-control: immutable`, CORS `*`.
  Источник заливки: `cf-assets/` (в git не коммитится). После первого деплоя адрес не
  открывался несколько минут (выпуск сертификата для нового поддомена) — это нормально.

## От чего отказываемся

- PHP/Symfony/Doctrine/Twig/MySQL на проде (остаются локальным инструментом экспорта).
- Живые данные: новый билд или правка текста = повторный экспорт + коммит.
- Серверное сравнение билдов: `TalentTreeComparer` переписывается на JS и считает в
  браузере по двум скачанным файлам (все пары предрасчитывать нереально).
- AssetMapper: Vue уже лежит как готовый ES-модуль, нужен только статический
  `<script type="importmap">`.

## Что остаётся клиентским как есть

Vue-остров дерева, слайдер уровня, лимит очков (`level - 9`), формулы
`{BASE + COEFF * Level}` (`scaled-formula.js`), word-diff описаний (`text-diff.js`),
настройки в localStorage, состояние дерева в URL.

## Формат данных

Не дамп таблиц: уже денормализованный и готовый к показу результат, по одному файлу на
пару билд×класс. База та же, что отдаёт текущий API-контроллер дерева, с двумя
изменениями под статику.

- `data/index.json` — группы билдов (представитель, члены), список классов (slug, имя,
  `iconPath`), карта «представитель × класс -> файл дерева». Из неё строится главная.
- `data/trees/<hash>.json` — вкладки -> таланты -> ранги. В рангах уже готовый текст
  описания (с развёрнутыми `$s1`-токенами и формулами `{BASE + COEFF * Level}`), поля
  активных способностей (цена, дальность, каст, кулдаун), требования стойки/оружия,
  пререквизиты, позиция в сетке, `sourceTalentId`.
- Изменения относительно нынешнего API:
  1. вместо готовых URL иконок — только хеш (`iconPath`), URL собирает клиент от базового CDN;
  2. в каждый ранг добавляется `spellId` — по нему JS-версия сравнения сопоставляет таланты
     между билдами (текущий ответ дерева его не содержит, он есть только у compare-API).
- Не попадает в JSON: внутренние служебные таблицы (`icon_sources`, миграции), пустые
  поля, всё, что клиенту не нужно для показа.

## Структура вывода (набросок)

Репозиторий (GitHub Pages):
```
index.html                         главная (список билдов, фильтр классов по билду)
tree/<build>/<class>/index.html    заглушка маршрута: представители групп, только существующие пары;
                                   для членов групп — редирект-заглушки на представителя
compare/index.html                 ОДНА страница, параметры в query: ?a=<build>&b=<build>&class=<slug>
assets/                            JS/CSS (app, talent-tree, compare-tree, ability-format, ...)
```

Cloudflare Pages (отдельный проект, не в git):
```
icons/<hash>.png   backgrounds/<hash>.png   class-icons/<hash>.png
data/index.json    data/trees/<hash>.json
_headers           CORS (Access-Control-Allow-Origin: *) для data/*, immutable-кэш для *.png
```
CORS нужен, потому что сайт на `github.io`, а JSON на другом origin. Иконки в `<img>` CORS
не требуют. PNG с именем-хешем кэшируются бессрочно, JSON — с короткой ревалидацией (его
имя от содержимого не зависит).

Compare нельзя сделать заглушками: пар билд×билд×класс ~18 000. Поэтому он живёт на одной
странице с query-параметрами, а красивые пути остаются только для `tree/...`.

## План работ

1. ГОТОВО. Команда `php bin/console app:export-static` в основном репозитории
   (`web/src/Command/ExportStaticCommand.php`, настройки `web/config/static-export.json`):
   группирует билды, пишет `data/index.json`, `data/trees/<hash>.json`, нужные картинки и
   `_headers` прямо в `cf-assets/`. Весь экспорт ~12 с (БД читается целиком за 6 запросов).
   Повторный запуск идемпотентен. Заглушки `tree/...` экспортёр НЕ пишет: их делает
   отдельный скрипт сборки сайта из `data/index.json` (пункт 2), чтобы экспортёр не знал
   про оболочку сайта.
2. ГОТОВО. Статическая оболочка (`docs/`): `index.html` + `home.js`, `compare/index.html`,
   `404.html`; `tools/build-site.php` генерирует `docs/tree/<представитель>/<класс>/` и
   редирект-заглушки для членов групп (сохраняют `?build=`). Пути относительные
   (`<html data-root>`), поэтому сайт работает под `/<repo>/` и на своём домене.
3. ГОТОВО. Клиент: `data.js` (загрузка с CDN, сборка URL картинок), `tree-page.js` (пикер и
   настройки), `compare-core.js` (порт `TalentTreeComparer` на JS), `config.js` (адрес CDN,
   для локальной отладки переопределяется ключом `wtv-cdn-base` в localStorage).
   Проверено в браузере и на локальной копии CDN, и на настоящем Cloudflare.
4. ГОТОВО. Cloudflare: Workers static assets `lucky-mud-f0cd.elsoldollo.workers.dev`,
   `_headers` (кэш и CORS) генерирует экспортёр.
5. ОСТАЛОСЬ. Публикация кода: создать репозиторий на GitHub, включить Pages из `/docs`,
   запушить. Экспорт и заливка на Cloudflare запускаются локально, т.к. GitHub Actions не
   достучится до приватной БД.
6. ОСТАЛОСЬ. Переэкстракция билдов (формулы вместо чисел в описаниях, исправленный
   `$s`-резолв) и повторный экспорт: группы билдов пересчитаются автоматически.

## Открытые вопросы

- Имя репозитория / базовый путь (`user.github.io/<repo>/` или свой домен).
- Нужно ли параллельно держать Symfony-версию, или standalone её заменяет.
- Раз JSON и иконки всё равно на Cloudflare Pages, можно держать там и код (один деплой,
  GitHub тогда только хранит исходники). Пока по умолчанию код остаётся на GitHub Pages.
